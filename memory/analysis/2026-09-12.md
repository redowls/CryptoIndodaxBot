## TOP FINDING: this routine's own equity command is wrong, and today it fired

`broker.get_account()` takes `price_by_symbol` and **values every coin balance
at zero when it is not supplied** (broker.py:104-123 — "Coins with no supplied
price are ignored rather than guessed"). The command written into the digest
routine calls it with no arguments. So:

| source | equity |
|---|---|
| routine's prescribed command | **Rp386.893** |
| `logs/trader.log` 16:14 (marks positions) | **Rp514.752** |
| hand-check: Rp386.893 cash + 0.00287667 ETH × Rp44.447.000 | **Rp514.752** |

Yesterday closed at Rp515.854 flat. Taken at face value the routine command
reports a **−25% one-day drawdown on a live-money account** that did not
happen; the real move is **−Rp1.102 (−0.21%)**, the ETH mark. The bot's own
trading path is correct — only the report is wrong, which is the worst shape
for this class of bug because the number that lies is the one a human reads.

This is the "cash-only trap" the 09-11 analysis predicted would fire as soon as
a position was open. It was open today, and it fired on the first try. The
trap is not that equity is hard to compute — the trader does it right every
hour — it is that **`get_account()` silently degrades instead of refusing**: a
missing price argument produces a plausible smaller number rather than an
error. Fix is one of: default `price_by_symbol` from the latest snapshot, or
return `equity=None` when balances exist without prices. Until then the digest
must read equity from `trader.log`, not from the bare call.

Correct account state: **equity Rp514.752, cash Rp386.893, 1 open (ETH),
Rp0 realized today** (zero exits).

## Yesterday's ETH call landed, by a different mechanism

09-11 flagged: *"tomorrow the day-change counter resets and LATE_ENTRY_DAY_PCT
stops protecting it, so an ETH fill buys the top of today's candle."* ETH
filled **09-11T19:14Z @ Rp44.540.000**. The outcome matched — high water since
entry is Rp44.762.000, just **+0.50%** above the fill, and it now sits −0.21%
— but the mechanism did not. The day counter never reset; ETH was rejected
`late entry +5.1%` (16:14) and `+5.4%` (17:14), then `1H close not green`
(18:14), then **filled at 19:14 when the day-% fell back under 5.0**.

That is the reusable part. `LATE_ENTRY_DAY_PCT` is not a "don't chase" rule,
it is a *"don't chase while the tape is still printing up"* rule: it releases
on the pullback in the same extended coin, i.e. precisely when the extended
move pauses. It gates the **timing** of chasing, not the chasing. An intraday
pullback in a +5% coin is the one condition that turns the filter off, so the
filter systematically hands back the entry near the local high. 8 lifetime
fires, so this is a mechanism note, not a bottleneck to tune (09-11 rule:
check lifetime fire count before calling a filter binding).
