## The finding that matters: the harness never tested what is running live

`risk_off` has been held four days on one result — regime_lab's docstring
(lines 38-42): *"What DID beat the live configuration was the AlwaysRiskOff
control, in all three windows including the bull run … the lead is in the entry
filter, not the regime clock."*

That result does not describe the live bot. Live `risk_off` does **six** things:

| effect | in replay? |
|---|---|
| green-on-day required | yes |
| 1H RSI <= 65 (vs 70) | yes |
| ADX bar 25 (vs 20) | yes |
| BTC excluded as regime driver | yes |
| trail 3.0xATR (vs 4.0x) | yes |
| **position size halved** | **NO** |

`replay.py:242` calls `risk.position_size(equity, price, atr, symbol=sym)` with
no `half=` argument. `trader.py:138` and `:163` pass `half=(reg == "risk_off")`.
`risk.position_size` halves `risk_idr` when `half=True` (risk.py:27-29).

So the harness measured AlwaysRiskOff's **entry filter at full size**. The thing
running live is that entry filter at **half** size, and the harness has never
scored it. The four-day override rests on evidence that is silent on its single
largest live effect. This is a harness defect, not a strategy conclusion — and
it is the reason I am **not** treating "AlwaysRiskOff wins in three windows" as
settled support for what is actually deployed.

I did not fix it here. The fix is one keyword argument in `replay.py:242`
(`half=(reg == "risk_off")`) plus a re-run of the three windows. That is a code
change, and it belongs to a session that can test it, not to a digest.

## What the half-size actually cost today — measured, and smaller than it looks

Both of today's winners were `half_size: true`. Counterfactual at full size,
using each trade's real entry equity and the same 0.63% round trip:

| trade | half net | full net | forgone | full/half qty |
|---|---|---|---|---|
| PEPE | Rp3.903 | Rp4.045 | **Rp143** | 1.04x |
| AVAX | Rp4.317 | Rp8.408 | **Rp4.091** | 1.95x |
| total | Rp8.220 | Rp12.454 | **Rp4.234** | |

My first estimate was "half sizing cost ~Rp8.2k, just double it." That was
wrong and the reason is structural and worth keeping:

**`max_notional = equity / MAX_POSITIONS` (risk.py:31) binds before full size
is reached on tight-stop coins.** PEPE's stop is 3.1% wide, so a full-size
1.5%-of-equity risk would need Rp240k of notional against a Rp123.582 cap — the
cap binds and full size is only 4% larger than half size. AVAX's stop is 5.7%
wide, so the cap binds much later and full size is nearly 2x.

The consequence: **`risk_off`'s half-sizing is close to a no-op on tight-stop
coins and a real ~50% haircut only on the wide-stop names** — AVAX, USELESS,
UNI, FARTCOIN, MOG. Those are precisely where this bot's wins come from (AVAX
alone is Rp9.425 of Rp29.773 lifetime net, 32%). The penalty is concentrated
exactly where the payoff is.

### Why risk_off is held despite the harness defect

The defect cuts both ways: it means the evidence does not *support* live
`risk_off`, but it equally means there is no evidence *against* its entry
filter, which the harness did test at full size and which won in all three
windows. Going to `auto` tonight would loosen four entry gates against the only
measured comparison that exists, on a real-money account, in order to get full
size on wide-stop coins — and the honest driver of that wish is the 14.8pp
benchmark gap, which I have just said is not a valid input. Held.

### Why max_positions goes 2 -> 4, and why that is not loosening

Yesterday capped slots at 2 and explicitly asked the next session to challenge
it. Two things changed:

1. **The stated reason expired.** The cap's rationale was "true win rate 28.6%,
   no demonstrated edge — capacity multiplies the rate at which a
   negative-expectancy engine trades." True win rate is now 41.2%, above the
   doctrine's own floor. Keeping a cap whose stated trigger has cleared is the
   same inconsistency as keeping a block whose release criterion is met.
2. **Under `risk_off` the risk arithmetic is identical.** 4 slots x 0.75%
   (halved `RISK_PCT`) = **3.0% aggregate risk** = 2 slots x 1.5% full size.
   Raising the count while `risk_off` halves each position restores capital
   utilisation *at the same total risk the 2-slot cap was protecting*. It also
   leaves `max_notional` untouched: that cap reads `config.MAX_POSITIONS` (4),
   not the policy value, so per-trade notional does not move at all.

The cost of the 2-cap was measured and large: the trader logged "no entry slots
(2 open)" and stopped evaluating coins for most of today, including the hours
when XRP was the cleanest setup on the board.
